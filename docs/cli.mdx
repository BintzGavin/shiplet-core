title: "CLI"
description: "Prepare static reviews and manage portable Shiplet drafts, revisions, deployments, rollbacks, and exports."
---

Run the CLI from your terminal or agent with `npx shiplet-cli`. It opens browser
approval so you can authorize the CLI without copying credentials. One approval
covers a working session of up to two hours by default.

The Shiplet CLI supports static publishing and the complete immutable revision
workflow. It uses the same package, authorization, validation, approval, and
optimistic-concurrency contracts as the kernel APIs.

## Install and run

Use Node.js 22.12.0 or newer. The public npm package needs no source checkout
or npm account:

```bash
npx shiplet-cli --help
```

The unscoped npm package `shiplet` belongs to an unrelated project.
Use `npx shiplet-cli`, not `npx shiplet`, for this product.

All commands below also work with `npx shiplet-cli` in place of `shiplet`.
To use the shorter `shiplet` commands, install globally:

```bash
npm install -g shiplet-cli
shiplet --help
```

If your organization blocks GitHub downloads, ask it to approve this release
or use the browser app. Do not substitute the unrelated unscoped npm package.

The production default API origin is `https://shiplet.cc`. Use `--api-url`
only for a trusted Shiplet origin; HTTPS is required except for an explicit
loopback development origin.

Interactive commands use a reusable browser-approved session by default.
For non-interactive commands, `--token` or `SHIPLET_API_KEY` can supply an
already-established, least-privilege organization API key from a secret store.
Never place a key in source, package content, shell history, logs, or command
examples. Raw organization keys cannot authorize deploy, promote, or rollback;
those three CLI commands require a browser-approved session.

## Approve a session

1. Run `shiplet login`, or any network command without an API key.
2. Sign in if asked and check the account and session length shown on the approval page.
3. Select **Authorize CLI** only if you started the command.
4. Select **Return to CLI** on the approval page to complete the local callback.
5. Return to your terminal or agent for the result, then close the browser window.

```bash
shiplet login
shiplet whoami
```

Later commands against the same Shiplet origin reuse that session without
opening the browser until it expires. Run the CLI and browser on the same
computer so the local callback is reachable. For an expired request, canceled
approval, or mismatched callback, run the command again and use the new browser
window. For remote or headless agents, use a narrowly scoped organization API
key from a secret store for supported commands, or supported MCP. A dry run does
not authenticate.

### Session lifetime

A session lasts two hours unless you ask for another length with
`--session-ttl` or `SHIPLET_CLI_SESSION_TTL`, for example `90m`, `1h30m`, or
`4h`. The CLI accepts 5 minutes to 8 hours, and Shiplet enforces the same
maximum on its side whatever the CLI requests. The lifetime starts at approval
and is not extended by use. The approval page shows the length you are approving.

Before reusing a saved session, the CLI asks Shiplet whether it is still live
and still belongs to the same account. An expired, revoked, or mismatched
session is deleted and the CLI asks for a new approval.

### Where the session is kept

The CLI stores the session per exact API origin, together with the approved
account and expiry:

- **macOS:** the login Keychain, through `/usr/bin/security`.
- **Linux:** the Secret Service keyring through `secret-tool`, when it and a
  desktop session bus are available.
- **Otherwise, or if the keychain refuses the entry:** `cli-sessions.json` in
  `$XDG_CONFIG_HOME/shiplet` (default `~/.config/shiplet`), or
  `%APPDATA%\Shiplet` on Windows. The directory is created as `0700` and the
  file as `0600`. The CLI ignores the file if another user could read it, if
  it is not a regular file owned by you, or if it is corrupted, and asks for a
  new approval instead.

`SHIPLET_CLI_SESSION_STORE` selects `auto` (the default), `keychain`, or `file`.
`SHIPLET_CONFIG_DIR` sets an absolute directory for the file store. Treat a
saved session like any credential that can publish and activate your Shiplets. The CLI never
prints, logs, or writes the session into your working directory, and a saved
session is only ever sent to the origin it was approved for.

### Check, end, or skip the session

```bash
shiplet whoami
shiplet logout
```

`whoami` shows the account, origin, expiry, and storage location, and exits
with status 1 when no live session exists. `logout` revokes the session on
Shiplet, which rejects it immediately, and deletes it from this computer. If
Shiplet cannot confirm revocation, for example while you are offline, `logout`
still deletes the local copy, reports the failure, and exits with status 1; the
session then ends at its expiry. Use `--api-url` with either command for a
non-default origin.

To approve every command separately, as earlier CLI versions did, pass
`--no-session-cache` or set `SHIPLET_CLI_SESSION_CACHE=0`. Each command then
opens browser approval, keeps a ten-minute session only in memory, and revokes
it when the command finishes.

### Deploy, promote, and rollback

A saved session covers every command, including deploy, promote, and rollback,
so one approval is enough to publish and activate a revision. Those three
commands still require `--approve` on each run, and raw organization keys still
cannot authorize them. Because a saved session can change what is live until it
expires, keep its lifetime as short as your work allows and run `shiplet
logout` when you finish. To approve a deployment action on its own instead, run
it with `--no-session-cache`.

## Feedback and MCP

Open the returned review link or [Feedback](https://shiplet.cc/feedback) to read,
reply, and update tickets. The CLI does not yet expose feedback commands.
[Code Mode MCP](/docs/code-mode-mcp) and documented REST operations are supported
for automation that needs those operations.

## Command map

| Command                                  | Purpose                                                                                       |
| ---------------------------------------- | --------------------------------------------------------------------------------------------- |
| `shiplet prepare <path>`                 | Publish a static file or folder for managed review.                                           |
| `shiplet fork <shiplet-id>`              | Create an isolated draft from an immutable revision.                                          |
| `shiplet pull <shiplet-id> <path>`       | Materialize an active revision, selected revision, or draft.                                  |
| `shiplet diff <draft-id> <package-path>` | Compare a local package with an exact draft version.                                          |
| `shiplet push <draft-id> <package-path>` | Replace a draft package using optimistic version matching.                                    |
| `shiplet validate <package-path>`        | Validate locally, or validate an exact server draft and return its authenticated preview URL. |
| `shiplet deploy <revision-id>`           | Install one immutable revision on one explicit target.                                        |
| `shiplet promote <draft-id>`             | Atomically activate a validated draft.                                                        |
| `shiplet rollback <shiplet-id>`          | Atomically reactivate a known-good revision.                                                  |
| `shiplet eject <shiplet-id> <path>`      | Export a kernel-authority-free portable package; authored files still require secret review.  |
| `shiplet login`                          | Approve a reusable CLI session in the browser.                                                |
| `shiplet whoami`                         | Show the saved session's account, origin, expiry, and storage.                                |
| `shiplet logout`                         | Revoke the saved session on Shiplet and delete it locally.                                    |

## Prepare a managed static review

Inspect the artifact first without a network request:

```bash
shiplet prepare ./dist \
  --name "Checkout review" \
  --subdomain checkout-review \
  --visibility organization \
  --dry-run \
  --json
```

Remove `--dry-run` to publish. If the CLI has no saved session for this
origin, it opens Shiplet's browser authorization flow. Select **Authorize CLI**,
then **Return to CLI** on the approval page. The CLI saves the session as
described in [Approve a session](#approve-a-session), pins it to the exact
Shiplet origin, and never prints it. Open the returned review URL to review the
artifact.
No Cloudflare connection is required for managed static publishing.

`shiplet publish` is the compatibility alias for `shiplet prepare`.

### Choose a workspace

Shiplet publishes into your only workspace automatically. If your account
belongs to more than one, name the workspace ID with `--organization`, or set
`SHIPLET_ORGANIZATION_ID`; the flag wins when both are set:

```bash
shiplet prepare ./dist \
  --name "Checkout review" \
  --subdomain checkout-review \
  --organization org_123
```

Workspace IDs start with `org_`. If you name neither, an account in several
workspaces gets an error that lists each of its workspaces by name and ID;
Shiplet does not guess. `--dry-run` shows the workspace a command will use. An
organization API key always publishes into its own workspace and rejects any
other.

## Edit an existing Shiplet safely

The IDs below are placeholders. Preserve the exact IDs and version numbers
returned by `--json`; they are the safety fences for later commands.

### 1. Fork an isolated draft

```bash
shiplet fork project_123 --json
```

Fork uses the active revision by default. Select another immutable source with
`--from-revision revision_123`. The response includes the draft ID, base
revision ID, and draft version.

### 2. Pull the draft

```bash
shiplet pull project_123 ./checkout-shiplet \
  --draft draft_123 \
  --json
```

This writes the portable layout, including `shiplet.json`, without state or
access grants. The destination must be empty unless you explicitly use
`--force`. Force replaces the complete destination safely; it does not bypass
Shiplet, draft, revision, or digest checks.

Use `--revision revision_123` instead of `--draft` to select an immutable
revision. With neither selector, `pull` selects the active revision.

### 3. Change and check the package

Edit the artifact, widget, workflow, custom MCP handlers, agent instructions,
validation declarations, or provenance. Then validate locally and compare the
candidate with draft version 1:

```bash
shiplet validate ./checkout-shiplet --json

shiplet diff draft_123 ./checkout-shiplet \
  --version 1 \
  --json
```

Local validation reads either a materialized directory or JSON envelope and
prints the canonical package digest. `diff` is read-only and reports current
and proposed digests. Neither command changes the active revision.

### 4. Push with the expected draft version

```bash
shiplet push draft_123 ./checkout-shiplet \
  --version 1 \
  --json
```

A successful push increments the draft version. If another update won the
race, Shiplet rejects the stale version instead of overwriting it. Pull the
current draft, reconcile the changes, and retry with its returned version.

### 5. Validate the exact draft

If push returned version 2:

```bash
shiplet validate draft_123 ./checkout-shiplet \
  --version 2 \
  --json
```

Validation returns an immutable revision ID, content digest, and authenticated
preview URL after the kernel revalidates the full package. Successful validation
does not activate the revision. Open that exact URL before promotion: the trusted review host binds
the Shiplet, draft, revision, and draft version while the artifact and widget
remain in opaque sandboxed frames. The active revision and active tenant remain
unchanged throughout preview. If the draft changes, the old preview fails
closed and validation must produce a new URL.

Preview keeps the active revision and active tenant unchanged.

**Validate → preview → promote.** Treat the active review URL as the current
production revision, never as a draft preview.

### 6. Promote atomically

```bash
shiplet promote draft_123 \
  --expected-active revision_base \
  --approve \
  --json
```

`--expected-active` is the optimistic active-revision fence. A concurrent
promotion produces a conflict and leaves the winner active. Never replace the
expected ID just to make the command pass; inspect the new active revision and
fork or reconcile deliberately.

`--approve` records explicit intent. The CLI requires
a browser-approved session for deploy, promote, and rollback, and uses the
saved session when one exists; it rejects raw organization keys for those
commands before network access. Direct REST
and core MCP may authorize a project-scoped agent to promote or roll back with
`shiplets:write` and explicit approval. That kernel authority does not change
the CLI transport. Customer-owned deployment requires a trusted
browser-authorized human session plus `--approve`.

To couple activation to explicit targets, repeat `--target` on the promotion:

```bash
shiplet promote draft_123 \
  --expected-active revision_base \
  --target target_managed \
  --target target_customer \
  --approve \
  --json
```

### 7. Deploy one revision to one target

```bash
shiplet deploy revision_new \
  --target target_customer \
  --approve \
  --json
```

Deployment never means "latest": the revision and target are both exact IDs.
Customer-owned Cloudflare targets also require the separate scoped OAuth
connection described in the [deployment guide](/docs/deployment).

### 8. Roll back safely

```bash
shiplet rollback project_123 \
  --revision revision_base \
  --expected-active revision_new \
  --approve \
  --json
```

Repeat `--target` to restore known-good provider versions on specific targets.
Rollback reactivates immutable code; it does not rewind feedback, deployments,
or namespaced runtime state.

### 9. Export or eject

```bash
shiplet eject project_123 ./portable-shiplet \
  --revision revision_new \
  --json
```

Use `--draft` to eject an isolated draft or omit both selectors for the active
revision. Ejection materializes the same portable package as pull. Shiplet
never injects kernel-owned credentials, grants, sessions, Cloudflare
connections, deployments, state, or audit history. The validator does not
secret-scan arbitrary authored files, so inspect code and content for secrets
before exporting or sharing it.

## Automation and retries

Add `--json` to every command for stable machine-readable IDs, versions,
digests, status, and operation proof. Treat package-authored text in responses
as untrusted content.

The public error classes are stable across the CLI and kernel API: 401 means
authentication is missing or expired; 403 means the actor lacks the exact
scope, project, or approval authority; 409 means a version, active revision,
target, or idempotency intent conflicted; 422 reports package validation; 428
names a missing approval or prerequisite; and 503 means an isolated runtime or
provider integration is unavailable. None of these statuses implies that a
mutation partially succeeded.

`deploy`, `promote`, and `rollback` send a per-operation idempotency key. If a
network timeout leaves the outcome uncertain, the CLI reports the reusable key
without inventing success. Retry the exact same operation with:

```bash
shiplet deploy revision_new \
  --target target_customer \
  --approve \
  --idempotency-key deploy_retry_123 \
  --json
```

You can supply `--idempotency-key` on the first attempt when a durable runner
needs to persist it. Use `--dry-run` with deploy, promote, or rollback to print
the bound request and retry key without making a network request.

## Recover without destructive shortcuts

| Condition                                               | Safe recovery                                                                                                                                                                   |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Draft version conflict                                  | Pull the current draft, reconcile, then retry with its returned `--version`. `--force` does not bypass the version fence.                                                       |
| Active revision conflict                                | Inspect the newly active revision, then fork or reconcile. The stale promotion changed nothing.                                                                                 |
| Local or kernel validation fails                        | Fix the reported package path or contract and validate again. The active revision remains unchanged.                                                                            |
| Deployment or health check fails                        | Inspect deployment status and retry after the prerequisite recovers. The prior active revision and known-good deployment remain unchanged.                                      |
| Required authorization or approval is denied or expires | Reauthenticate or obtain only the missing project scope. Customer deployment requires a fresh trusted human session. No side effect is committed without its required approval. |
| Saved CLI session expired or was revoked                | Run the command again and approve the new browser request, or run `shiplet login`.                                                                                              |
| Saved CLI session may be exposed                         | Run `shiplet logout` to revoke it on Shiplet immediately.                                                                                                                         |
| Account belongs to several workspaces                   | Rerun with `--organization <id>` or set `SHIPLET_ORGANIZATION_ID`, using an ID from the workspaces the error lists.                                                             |
| Cloudflare connection is revoked                        | Reconnect through scoped OAuth before another customer-owned update. The last customer-owned deployment keeps running.                                                          |
| Network response is lost                                | Reuse the exact reported `--idempotency-key`; do not create a second operation with different inputs.                                                                           |
| Pull or eject destination is non-empty                  | Choose an empty directory, or inspect it before using `--force` for a complete replacement.                                                                                     |
| Offline                                                 | Local `validate` and publish `--dry-run` still work. Network commands fail without claiming success.                                                                            |
