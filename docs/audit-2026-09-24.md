# Shiplet reliability and product audit

Date: 2026-09-24. Baseline: `625480c`.

## Recommendation

Make the existing review loop dependable before adding features. Preserve the
static-first product, isolated artifact frames, existing D1/R2 boundaries, and
current UI. Fix observable failure behavior with small changes and regression
tests. No new dependencies or architecture rewrite are warranted by this audit.

```text
Publish artifact → share a usable link → save feedback → act on a ticket
       ↓                  ↓                  ↓                ↓
 recover failures     truthful copy     atomic persistence   focused follow-up
```

## Scope and evidence

This is a repository audit, not a production penetration test or operated
deployment review. Four parallel review tracks covered product/frontend flows,
API/data lifecycle, operations/test coverage, and authentication/trust boundaries.
The review sampled the implementation and traced the paths listed below; it
does not claim exhaustive line-by-line coverage of every advanced runtime,
CLI command, or MCP tool.

The clean baseline passed `npm run verify`: 98 Vitest files / 1,787 tests,
25 Node script tests, generated-type checks, TypeScript, main/support Worker
dry-runs, license checks, and dependency audit (zero reported vulnerabilities).
Browser and mutation checks are separate from that gate.

Strong existing foundations: opaque artifact/widget isolation, explicit
capabilities, guarded advanced runtime activation, public URL/redirect validation,
static-first self-hosting, and extensive negative security tests. Preserve these.
The 19,698-line baseline `src/index.ts` is a maintenance concern, but splitting it
without a behavior-driven reason would expand this change without fixing a user
problem.

## Selected behavior specification

1. Given an owned deployment config and supported options, when the wrapper runs,
   then the exact environment/dry-run intent reaches Wrangler. Unknown or
   ambiguous arguments launch no deployment.
2. Given an explicit invalid, expired, revoked, or out-of-scope CLI credential
   alongside a valid browser session, when authentication runs, then browser
   authority is not used. Cookie-only and valid scoped CLI requests keep working.
   A malformed unrelated cookie must not cause a server error.
3. Given two distinct concurrent feedback submissions, when both succeed, then
   both feedback records and canonical events exist with distinct ticket numbers.
   A failed save must never receive a successful null response. Duplicate client
   IDs retain the existing retry/fencing contract.
4. Given a nonexistent feedback ID, when its status is changed, then the response
   is not found and no canonical event is added. Given a screenshot followed by
   rejected persistence, no newly uploaded screenshot remains in the review bucket.
5. Given an archived artifact whose DB purge fails, when deletion is attempted,
   then its assets remain intact and it can be restored. External cleanup happens
   only after DB success. A detected cleanup failure must be distinguished from a
   failed record deletion.
6. Given a review URL copied on path-based hosting, when copying succeeds, then
   the clipboard contains an absolute URL. Failure must not announce success,
   there is one copy attempt path per control, and the accessible name is restored.

Tests must demonstrate failure before production edits and pass afterward.
Use real local Workers/D1 behavior for persistence and route boundaries, and a
fake Wrangler for deployment tests. No live deployment is part of this work.

## Deliberate limits

The deletion mitigation does not define a new audit-retention policy or repair
the entire purge dependency graph. Some projects will still reject permanent
deletion safely. A process crash after committed deletion can leave external
objects or a domain behind until a durable cleanup mechanism is designed.

Cross-service publication recovery, setup recovery, and signing-key rotation
deserve their own fault-injection work. A generic retry or broad exception
handler would conceal partial effects rather than establish correctness.

D1 batch rollback behavior was checked against the
[official D1 API documentation](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch).
Production provider behavior, authorization configuration, capacity/performance,
assistive-technology behavior, and operated rollback remain unverified here.

## Verification results

Tests were written before production changes. The initial auth run failed 11
regressions while passing three valid-behavior controls; the initial persistence
run failed all seven cases; both clipboard browser tests failed; and the
deployment subprocess test caught discarded options. The fixed focused suites
pass, including scope/fence boundaries, repeated client IDs, mention hydration,
missing/empty ticket IDs, both insert failure points, and cleanup failures.

An existing metadata test formerly relied on invalid bearer fallback to test
identity. It now explicitly verifies 401 before any origin fetch, followed by
successful cookie-context metadata inspection with no credentials forwarded.
The outbound credential-stripping assertions remain intact.

Seven targeted fault-reintroduction mutations were killed (7/7, zero survivors)
against isolated temporary copies. They remove the authorization guard, restore
cookie exceptions, force ticket collisions, use the wrong screenshot bucket,
emit missing-ticket events, delete assets before a failed purge, and separate
feedback/event commits. The 25-test unmutated baseline passed. This is focused
mutation evidence, not a whole-repository mutation score.

Jev's isolated Chromium smoke completed landing-page-to-documentation navigation.
The clipboard browser suite passed 2/2, including one write per click, absolute
URLs, native rejection with successful fallback, fallback false/throw, and
accessible-name restoration after rapid retries.

The integrated `npm run verify` gate passed: **100 Vitest files / 1,812 tests,
26 Node script tests, type checking, all Worker dry-runs, license checks, and zero
reported dependency vulnerabilities**. `git diff --check` passed.

The expanded browser run exposed two stale annotation selectors left behind by
the existing shared-control UI: the tests still requested “Markup screenshot”
while the control is “Draw on screenshot.” Both selectors were corrected without
changing their interaction assertions. Runs concurrent with other local Workers
verification also lost their Wrangler proxy, causing later connection failures;
they are not treated as passing evidence.

An expanded 27-test browser selection stopped after two failures: a missing
“Open file” link for a no-index artifact and a missing custom-widget frame in the
stalled-widget fixture (17 passed, two failed, eight unrun). Both exact
missing-element failures reproduced in an exported copy of baseline `625480c`.
That comparison used the same local toolchain; it does not resolve the underlying
product-versus-fixture mismatch. These paths remain open and the entire browser
suite is not claimed green.

The focused browser checks now pass **18/18 across isolated runs**: 15 checks
cover authentication/navigation, publishing/archive/restore, feedback/inbox,
trusted confirmation, and screenshot annotation; the final three cover clipboard
behavior and URL metadata autofill. The metadata test also needed to open the
existing “Experimental options” disclosure before selecting the URL mode. Its
autofill and preservation-of-human-edits assertions were unchanged. Browser
recordings and scratch verification harnesses were kept outside the repository.

Useful rerun commands:

```bash
npm run verify
npx vitest run test/auth-boundaries.spec.ts test/review-reliability.spec.ts
npm run build:platform-client
npx playwright test e2e/clipboard-behavior.spec.ts e2e/url-metadata-autofill.spec.ts
```

Estimated confidence in the selected local changes: **95%**. Verified claims are
limited to the source, local runtime, subprocess, browser, and mutation checks
above. Remaining product improvements are the explicitly open rows in the
finding table. The highest-value next implementation is publication recovery:
reject invalid input before writes and prove a failed creation can be retried
under the same subdomain without leaving an unusable project.

Routing used senior reviewers for the audit and security/data changes, a routine
implementation worker for deployment/clipboard fixes, and independent review
plus executable verification. The model-router service was unreachable in the
initial invocation, so its documented fallback rubric was used.

## Follow-up: repeated authentication and feedback confirmation

The user's next priority was repeat authentication and the extra tab required to
submit ordinary feedback. [The follow-up specification](review-friction.md)
records the selected changes and their verification separately: reuse valid
browser sessions, save managed built-in feedback inline, preserve failed drafts,
and keep retries idempotent through the existing transactional intent fence.
Third-party embeds and custom-widget actions retain their distinct confirmation
boundary. The original verification totals above describe the preceding audit
batch; the follow-up document records the combined gate after these changes.
